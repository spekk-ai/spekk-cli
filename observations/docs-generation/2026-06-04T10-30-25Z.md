# Three-Site Documentation Model Is a Poor Fit for CLI Developer Tool

## Issue Description

The docs-generation skill assumes a web application architecture with distinct audiences (engineers, QA testers, end users). Spekk CLI is a **Go CLI binary** used exclusively by software engineers. The deterministic checks from the skill workflow reveal this mismatch clearly.

## Evidence

Deterministic check results showing this is not a web app:

| Check | Result | Implication |
|-------|--------|-------------|
| `openapi.json` or swagger | Not found | No REST API to document for engineering or QA |
| `client/src/pages/` or route config | Not found | No frontend pages to map to user journeys |
| `server/` or backend entry point | Not applicable | Go CLI binary, not a web server |
| `docker-compose.yml` | Not found | No container-based dev setup |
| `.env.example` | Not found | Env vars documented in `docs/configuration.md` instead |
| `e2e/` or playwright config | Not found | No browser-based E2E tests |
| Frontend routes | Not applicable | CLI commands are the "routes" — already documented in `cli-reference.md` |

**Why each proposed site doesn't fit:**

1. **Engineering docs (`docs-engineering/`)** — The existing `docs/` site IS engineering docs. It covers installation, concepts, CLI reference, skills, and configuration. The audience for Spekk CLI documentation is 100% engineers.

2. **QA docs (`docs-qa/`)** — QA for a CLI tool means running commands and checking output, which is better handled by automated tests (`go test ./...`). There's no web UI with pages to manually click through. The `spekk show` web viewer is read-only and auto-generated. A release testing checklist could be a single page, not an entire site.

3. **User docs (`docs-user/`)** — The "users" of Spekk CLI are the same engineers who would read the engineering docs. Writing "How to use the coach" in non-technical language for a tool that requires Claude CLI, Git, and Go installed makes no sense. The existing `getting-started.md` and `concepts.md` already serve this purpose perfectly.

## Impact

Generating three separate Zensical sites would:
- Triple documentation maintenance burden with no additional audience reached
- Create artificial audience distinctions that don't exist for this project
- Fragment content that benefits from being cross-referenced in one place (e.g., concepts page links to CLI reference, which links to skills guide)
- Contradict the project's lean philosophy ("only three priority levels", "keep assertions atomic")

## Recommendation

1. **Do not create `docs-engineering/`, `docs-qa/`, or `docs-user/` directories** for this project
2. **Invest in the existing `docs/` site** — it's well-structured and appropriate for the single audience
3. **If the docs-generation skill is meant to be used on other projects** (web apps with distinct user types), consider adding a pre-check that evaluates project type before proposing the three-site model
4. The skill could be adapted to detect CLI-tool patterns (single binary, no frontend, no API schema) and recommend a single enhanced site instead
