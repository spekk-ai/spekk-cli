# Existing Docs Site Already Covers Most Engineering and User Needs

## Issue Description

The docs-generation skill prescribes three separate Zensical documentation sites (engineering, QA, user). However, Spekk CLI already has a well-structured Zensical docs site in `docs/` with `zensical.toml` at the project root. The existing site covers: getting started, core concepts, CLI reference, skills guide, configuration, and 6 versioned release notes. For a **CLI developer tool** whose users are exclusively engineers, the current single-site approach is appropriate and largely complete.

## Evidence

Current `docs/` site contents (all served via Zensical):

| Page | Coverage |
|------|----------|
| `index.md` | Project overview, quick start, command table, agent descriptions, philosophy |
| `getting-started.md` | Installation (4 platforms), first spec workflow, common workflows |
| `concepts.md` | Specs, assertions, frontmatter fields, priorities, dependencies, branches, writing guidelines |
| `cli-reference.md` | All 10 commands documented with flags, examples, and behavior details |
| `coach-skills.md` | Skill discovery, 3 built-in skills, custom skill creation guide |
| `configuration.md` | Prompt customization (extend/override), directory structure, env vars |
| `release-notes/` | 6 release notes (v1.1.0 through v1.4.0) |

The `zensical.toml` is fully configured with navigation, theme, features (code annotations, copy, tooltips, mermaid, search highlighting, etc.).

## Impact

Creating three separate doc sites would fragment well-organized documentation that currently lives in one place. For a CLI tool where users = developers, the overhead of maintaining three separate sites outweighs the benefit. The existing single site already serves as both "engineering docs" and "user docs" since the audiences are identical.

## Recommendation

Instead of creating three separate sites, consider these targeted improvements to the existing `docs/` site:
1. Add an **Architecture** section (internal package overview, data flow, parser internals)
2. Add a **Contributing** page (migrate content from `CONTRIBUTING.md` into the Zensical site)
3. Add an **Observer Agent** page (currently underdocumented compared to coach and builder)
4. Add a **Troubleshooting / FAQ** page for common issues
5. If a QA testing checklist is needed for releases, add it as a single page under the existing site rather than a separate site
